# Oriward 优化改造计划书

日期：2026-10-31  
状态：P0/P1 核心改造及 P2 工作流已实施并完成本地工程验收；P3 真人试用与市场验证尚未开展。  
依据：本轮产品定位、简历生成体验及确认流程讨论；结合本地工作区代码与契约检查。本文由用户明确要求建立，作为阶段性实施计划，不替代当前运行契约。实施后将有效规则合并回现有文档，避免长期维护两套规则。

## 一、改造目标与已经确定的方向

Oriward 的重点从“面向在校生、应届生的求职成长工作台”，转向帮助经历丰富、正在重新求职或转向的人，通过对话找回经历、发现价值，把过去的积累转化为现在能够表达和使用的职业材料。

宣传词：

> 这些事我确实做过，但以前不知道它们值得写，也不知道可以这样表达。

这句话表达产品希望带来的体验，不作为已发生的用户证言。已纳入 v0.4.0 的 README、海报与公开宣传文案。

本次改造的首要交付不是更多审批流程或更复杂的职业评分，而是：用户不用先写好履历，也不用逐条批准经历；通过自然对话形成可持续使用的经历库，再得到一份履历完整、重点鲜明、表达充分、结构像简历的成稿。

### 已确定的产品原则

- 先理解完整经历，再围绕岗位组织表达，不能用关键词筛选代替理解。
- 用户明确讲述的事情可以直接整理、保存和使用；不增加“经历获准”步骤。
- 正常的提炼、归纳、专业表达和真实基础上的包装由 AI 直接完成，用户看完整稿后再提出修改。
- 不要求用户提交证明附件、精确 KPI 或重复认可自己已经讲过的话。
- 来源与版本在后台保留，用于接续和修改，不转化为面向用户的证据评级或使用门槛。
- 不随意删除表面上不相关的经历，不遗漏教育等已有基础信息，不通过编辑制造履历断档。
- 不能凭空增加学校、任职、职责、工具、数字或结果；但也不能因为缺少外部证明就把用户自述降为不可用材料。
- 用户的更正和“不想展示这段”直接生效，不再增加一次批准动作。

### 本轮讨论中已被后续意见替代的建议

“保留获准门槛作为过渡”不再采用；“所有经历必须逐条获准后才可用于简历”应移除。“简历有取舍”调整为先理解、再表达、再分配篇幅，不得成为自动删经历的理由。不得以“可用性评审”“事实审核”等新名称重建同类门槛。

## 二、目标人群与尚待验证的假设

第一轮不缩窄到单一人群，平行观察两类使用者：

| 人群 | 典型情境 | 需要验证的价值 |
| --- | --- | --- |
| 长期工作后重新求职或转向的人 | 经历多、简历陈旧、对外表达沿用过去行业的话语 | 能否找出迁移价值，并组织成新岗位看得懂的简历 |
| 经历零散或离岗后重返职场的人 | 个体经营、零工、家庭照护、非标准就业等经历难以整理 | 能否恢复职业脉络，表达实际做过的事情和已有能力 |

中年再求职者是重点关注对象，但不设置年龄准入，也不排除存在同类需求的年轻人。不把“应届生已经被招聘平台完全满足”“中年用户一定愿意付费”“老龄化必然带来需求”写成结论。本计划未进行市场调研，以上市场判断仍需实际使用反馈。

验证时同时观察入口负担。现有 Agent + 本地 CLI 的形态可以先用于试用，但不能把安装和配置困难归因于用户不需要产品。首轮由有人协助的使用流程验证价值，单独记录接入成本，再决定是否需要新的界面。

## 三、改造前的问题基线

初版计划制定时，仓库已有一批未提交的简历生成、模板与导出修改。以下保留当时的问题基线；当前改造与验收结果见 CHANGELOG，不将旧行为误作现行规则。

| 当前情况 | 造成的问题 | 改造方向 |
| --- | --- | --- |
| 新经历的 `approved_for_resume` 默认 false；用于简历前检查该字段、evidence 及其状态 | 用户已经说过的内容仍可能被整体挡住；一个未明确的点也可能影响整段经历 | 移除逐条经历审批与整段证据状态门槛，以用户讲述为正常材料 |
| 简历生成要求每段当前获准经历都出现 | 能防止部分误删，却不能保证理解、表达和篇幅分配 | 全库盘点与简历详略分开，不再围绕“获准清单”工作 |
| 教育等个人资料栏目可选，内容要求来自特定核准摘要字段 | 已有资料可能因字段或输入方式而遗漏，表达也受限 | 从现有个人资料与用户讲述组织完整板块，支持有来源的自然改写 |
| 定制包用固定预算取一批索引，再加载其详情 | 丰富经历库存在分页遗漏或上下文膨胀风险 | 完整遍历索引、分批读细节，明确实际处理范围 |
| 模板和技能示例仍偏学生、课程与实习；默认固定个人参考结构 | 可能把其他人的职业史强行塞入学生简历 | 保留既有个人模板偏好，通用流程按履历结构组织 |
| 现有规则强调来源、审核和硬约束 | 容易把“可追溯”误做成“未经批准不可使用” | 后台保留记录，前台减少流程，检查着重遗漏和成稿质量 |

核对入口：[经历库](../oriward/experience_library.py)、[简历生成](../oriward/resume_content.py)、[经历整理技能](../.agents/skills/career-discovery/SKILL.md)、[简历技能](../.agents/skills/resume-builder/SKILL.md)、[数据契约](DATA_MODEL.md)。

## 四、目标使用流程

**自然讲述 → 经历自动整理入库 → 理解岗位 → 重新组织表达 → 输出完整简历 → 用户看稿修改 → 继续积累。**

### 1. 用对话恢复经历

允许用户从任何一件事讲起，不要求按时间顺序填完所有字段。AI 随对话整理“当时做什么、自己做了什么、结果如何、时间和组织”等已有信息；缺失内容可以暂空，不因没有量化结果而阻止保存。

提问用于帮助回忆、挖掘内容或澄清会明显改变表达的歧义，不作为每段经历的必经程序。已有材料、已有回答和用户更正应复用；一次只追问最有帮助的缺口。记录当前话题，允许暂停和下次继续。

默认建立事件级经历和简略时间线，避免每一句话都变成独立经历。用户补充同一件事时更新原条目，岗位文案另存，不能反过来改写原始经历。

### 2. 取消经历审批，保留自然修改

用户直接讲述的事实及忠实整理后的表达可立即使用。可以直接把口语转成专业表达、突出动作与贡献、归纳可迁移能力；不要求每条先经过批准，不把缺少附件视为缺乏资格。

不为整个经历库建立一套“已验证／未验证”使用队列。来源信息用于区分用户原话与 AI 自己提出的方向想法；普通用户自述不等于外部核实，但足以制作简历。后台保持真实来源标签即可，不要伪造一次用户确认来让旧命令通过。

如果用户只说“负责进货”，可以据上下文写成“负责日常采购与补货安排”；不能自行增加“降低成本 30%”。如果某个数字或职责归属不清，先用已知事实写出可用稿，确有必要时只问那个点，不能冻结整段经历或整份简历。

完整初稿直接交给用户阅读和修改。不得把“用户还没看稿”变成不能生成或导出供其查看的理由；也不得把未收到回复记成用户已确认。对外投递和上传仍是独立操作，不由生成简历自动触发。

### 3. 先搭完整骨架，再理解岗位

生成前检查已有个人资料和经历索引，形成教育、主要职业阶段、项目及其他相关活动的整体脉络。覆盖整个索引，不能把一次预算内返回当成全部经历。

针对目标岗位，理解工作目的和 2–4 项核心交付，再逐段寻找实际动作与要求之间的联系。判断依据是做过什么、承担什么、解决什么问题，而不只是职位名称、行业名称和 JD 关键词是否一致。

没有明确目标时，可以先整理通用简历或提出少量方向线索，不为获得一个 JD 而强迫用户先完成职业选择。

### 4. 用详略分配代替粗暴删除

| 经历作用 | 默认呈现方式 |
| --- | --- |
| 直接体现岗位核心交付 | 重点展开，写清动作、方法、职责及已知结果 |
| 行业不同但能体现迁移能力 | 提炼并解释与岗位有关的真实工作内容 |
| 主要承担职业时间线作用 | 简述组织、角色、时间和必要职责，保留职业阶段 |
| 同一职业阶段的重复或细碎事件 | 可以整合表达，但后台保留对应来源，不能把不同单位或身份混成一段 |
| 用户明确不希望展示的内容 | 按用户要求不展示，不反复追问，不因完整性规则强制加回 |

默认不因低相关就删除一整段主要职业阶段。细小事件不必逐条成为简历条目，但应先被理解，再决定合并或简述。系统内部可记录其呈现位置，用户无需逐项审批这张映射表。

工作履历默认按时间倒序展示，重点通过段内内容和篇幅体现；精选项目可按相关性组织，但必须保留所属单位和时间，不能把真实时间关系打乱。允许真实空档和重叠任职，不猜日期、不虚构填补，不把空档本身判为缺陷。私人空档原因不自动写进简历。

例如，门店经营经历中实际包含采购、库存、人员协调和客户维护时，可以在申请相关运营岗位时突出这些工作；不能因为“不是同一行业”就整段删除，也不能擅自改成没有担任过的管理头衔。

### 5. 输出完整、自然的简历

已有的姓名、联系方式、教育信息应正常呈现；工作、经营、项目、技能及证书等板块按实际材料组织。教育经历不能因为与 JD 关系弱而消失；没有证书、实习或兴趣材料时，不创建空标题凑板块。

尊重用户已经指定的模板；没有指定时，根据履历类型安排板块，而不是把某一位用户的个人参考简历推广为全产品固定结构。有长期工作经历的人可把工作放在教育前，学生可把教育和项目放在前面。

先保证信息结构，再做排版。不机械压成一页，也不靠重复表述或虚构内容填满页面。若页面过空，先回看是否漏了已有内容、表达是否过度压缩；若过长，先去重复、调整详略。正文不夹带来源 ID、审批状态、内部路径或审核说明。

### 6. 将经验接到新方向和学习任务

从已有经历提出相邻行业、新岗位或混合技能方向，但在缺乏市场证据时明确其探索性质，不保证“学一点新技术就一定转型成功”。岗位验证与学习安排在用户需要时展开，不阻碍当前简历完成。

学习计划围绕具体任务：已有能力是什么、补哪项工具或知识、做出什么东西、如何判断能用、需要多少时间。优先小型实践和真实产出，不堆课程清单。按用户实际精力安排，避免默认学生考试周期或全职学习条件。

## 五、工程改造与兼容方案

### A. 经历与个人资料入口

- 调整经历写入和读取流程：普通对话自述自动保存来源，不要求手填 evidence、先做批准或补材料才能使用。
- `approved_for_resume` 退出新流程的使用判断；旧字段保留兼容与历史含义，不批量改成 true 来伪造“已批准”。
- 旧记录中来源明确的用户讲述正常可用；明确排除、撤回、替代的记录继续尊重原状态。来源不明的导入内容不批量升级为用户自述，也不生成全库待核验任务，只在实际使用且影响表述时处理。
- 把用户对事实的更正与对某份简历的文案调整分开：前者更新原经历并影响后续使用，后者保留在该简历版本。

### B. 内容组织与接口

- `resume tailor-packet` 从“获准经历列表”改为完整经历盘点入口，提供当前资料、索引分页状态、岗位目的和按需细节入口；旧字段兼容返回时明确其过渡含义。
- `resume compose` 支持展开、简述和同阶段整合；段落可引用多个来源经历，保留逐条表达对应的来源关系。呈现覆盖信息随简历版本保存，不要求用户批准覆盖表。
- 删除“所有获准 ID 必须各自出现一次”的硬编码；改成内部检查主要职业阶段和已有基础资料是否被意外漏掉，发现后先自动修复。不得把来源不完整的细碎事件当成禁止生成的错误。
- 个人资料栏目允许从已有用户事实自然整理和改写，不再只允许某一摘要字符串的逐字摘录。扩展来源支持时继续保留用户事实与岗位措辞的区别。
- 来源映射由系统随整理过程维护，优先引用稳定经历 ID、版本和相关原话；不要求用户提供逐句引文，不把“不是原文逐字复述”判为待审批，不因某个表达缺少独立证明而退回保守措辞。
- 各入口统一使用新规则，包括直接组合、旧版 build、修改、评审、导出及申请材料准备，不能只改 compose 后在后续入口重新出现审批阻断。

### C. 检查、状态与导出

- 默认检查聚焦遗漏、时间关系、明显事实改写错误、重复内容、栏目结构和可读性；能自动修复的直接修复，不向用户展示长清单。
- 取消以经历审批布尔值、混合 evidence 状态或缺少逐条事实确认来阻断正常成稿的逻辑。检查用于帮助完成简历，不作为独立的用户流程阶段。
- 连同下游 `factual_status`、confirm 及类似逻辑一起调整，不能经历库已放行、普通包装却又自动进入 pending；不得单靠词语变化、工具词命中等启发式规则认定新增事实并要求用户审批。
- “已生成”“有用户修改”“存在某个待补细节”等描述工作进度，不暗示已经通过雇主验证或用户批准。不通过新增状态机重建审批链。
- 普通写稿不强制先完成整套模拟招聘审查；该能力保留给需要岗位评估或面试准备的场景。不得为追求模拟评级而删掉真实经历或过度收缩表达。
- 导出支持用户阅读初稿与修改稿；技术错误仍需报告，但缺少“用户已审阅”不阻止本地预览。继续逐页检查版式，不把生成成功等同于排版良好。

### D. 迁移与文档同步

保持 Agent + Python CLI + SQLite 架构，核心仍仅依赖标准库；不在本轮引入模型服务、后台任务或新连接器。新增存储字段通过现有迁移机制添加并备份，不直接修改用户数据库行，不重写历史简历或删除私人材料。

来源版本和修改历史继续保存，但不要求用户为每次普通改写重新授权。旧输出保留；新流程产生新版本。个人固定模板偏好继续有效，通用默认规则单独调整。

同步修改 AGENTS、相关 Skills、WORKFLOWS、DATA_MODEL、README 与 CHANGELOG，避免代码取消审批而技能还要求批准。当前未提交改动先逐项核对归属，在其基础上整合，不覆盖或回退其他工作。

## 六、实施顺序与阶段交付

| 阶段 | 工作内容 | 完成条件 |
| --- | --- | --- |
| P0：取消重复审批 | 梳理所有经历使用入口，移除逐条批准和整段证据状态阻断，补普通自述的自然入库路径 | 虚构用户讲述后，无额外批准即可生成并导出供阅读的初稿；没有换名的审批步骤 |
| P1：生成完整简历 | 完整索引遍历、履历骨架、教育等资料补全、详略与整合、源映射、整体排版 | 典型复杂履历不漏主要阶段，不因行业不同误删，成稿可阅读且有重点 |
| P2：改进对话与表达 | 轻量追问、暂停恢复、同事件补充、迁移能力表达、用户看稿反馈 | 用户无需自己先填履历表；修改不丢失，复用经历不需重新讲述 |
| P3：验证新定位 | 两类目标人群试用，观察经历挖掘、表达和操作负担；同步探索方向与小型学习任务 | 收集实际使用证据，明确下一轮优先人群、是否需要新入口及主要改进点 |

P0 与 P1 形成第一批可交付改造。P2 可在此基础上继续，P3 的访谈可以并行准备，但未验证前不发布“更适合中年人”“提升录用率”等结论。

本轮不默认开发独立 App、原生语音录音、自动投递、付费体系或复杂打分引擎。语音输入可以借用宿主已有能力，但不能宣称产品已经提供原生语音功能。确需新建较大模块时，再做适度现有方案和 GitHub 项目调研。

## 七、验证与验收

### 功能回归场景

| 场景 | 预期结果 |
| --- | --- |
| 用户只通过对话讲述，无附件、无精确 KPI | 自动整理入库并生成可用简历，不要求经历获准 |

### 三层验收

1. **工程层**：使用虚构用户和隔离 `ORIWARD_DB`。源码修改后运行 `python -m unittest discover -s tests -v`，补上述真实行为回归；验证迁移、旧接口兼容和修改历史。涉及导出时安装可选依赖实际生成并逐页检查，跳过不算通过。
2. **交互层**：在真实 Agent 对话中跑至少两种虚构履历，包含暂停恢复、纠正、跨岗位改写和导出。确认没有隐藏的批准请求，不能用直接向数据库预填“全部已获准”的测试代替实际体验。
3. **用户层**：建议首轮两类人群各邀请 3–5 位自愿试用者，作为探索样本，不用于证明总体市场规模或就业效果。记录他们能否认出自己的真实经历、是否发现值得写的内容、是否省去了自己组织材料的负担，以及哪些表述仍需修改。

工程验收要求：标准自述流程中的额外经历审批次数为 0；测试样本已知的教育及主要职业阶段无意外遗漏；不凭空增加事实；所有本轮必要检查完成。表达是否有帮助由实际看稿反馈判断，不用单一自动分数替代。

记录有效操作时间、重复追问次数、用户修改原因和页面问题，区分工具耗时与用户讲述时间。不设置未经验证的“省时百分比”或“面试率提升”宣传指标。若用户仍感到被审问、需要先自己整理，或成稿仍空洞，就继续修复对应环节，不能仅以单测通过宣布体验完成。
